# Security model and remaining risks

Assets include submitted certificates, OCR text, user identities, JWT signing key and stored objects. Trust boundaries include browser→API, API→object store/database, and Kafka→workers. Authentication uses bcrypt and signed access JWTs with required subject/issue/expiry claims. Passwords above 72 UTF-8 bytes are rejected to prevent bcrypt truncation; accounts previously created with longer passwords need an administrative recovery process, which is not implemented. Tokens expire but cannot be revoked server-side; there is no refresh-token flow, password reset or login throttling. Registration discloses duplicate accounts.

Status, report and heatmap endpoints return 404 for another owner. Uploads use generated object paths, allowed MIME/extension/magic, capped handler read, image decoding and 20-million-pixel limit. PDFs only have signature-level checks. Multipart parsing may spool data before the handler cap: configure a reverse-proxy request-size cap, rate limits, sandboxed OCR, malware scanning and storage quotas before exposing the application. Local development credentials and ports in Compose are not production secrets; never deploy unchanged. Redis rate limiting fails open.

Kafka and local object storage do not use transport encryption or authentication suitable for hostile networks. OCR data is persisted in Postgres; new broker event payloads contain IDs and object keys, not OCR text, but legacy events/DLQs can contain sensitive data. DLQs and outbox should be access-restricted and retained only as needed. No claim of full security, privacy compliance or vulnerability-free dependencies is made. Readiness, reprocessing, audit logging, encryption/key rotation and object reconciliation need further work. Testing covers selected API ownership, validation, token and failure cases, not an independent penetration test.

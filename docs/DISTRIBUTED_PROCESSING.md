# Distributed processing and failure windows

The database outbox covers the three domain transitions: `certificate_uploaded`, `ocr_completed` and `analysis_completed`. API upload commits analysis + outbox; OCR and forensics hold an analysis row lock and commit their state + corresponding outbox row. The OCR process starts a daemon dispatcher thread with its own producer and DB sessions. A PostgreSQL `FOR UPDATE SKIP LOCKED` claim protects against two dispatchers publishing the same currently locked row. `sent_at` is written only after a broker delivery acknowledgement. On a failed acknowledgement the row remains pending and is retried; a crash after acknowledgement but before DB commit can cause duplicate publication. A queued producer message may arrive after a timeout. The design therefore needs idempotent consumers and is not exactly-once. Existing analyses stuck before this upgrade are not automatically reconstructed or replayed.

Workers disable Kafka auto-commit, process sequentially, and synchronously commit a message after success/duplicate or confirmed dead-letter plus terminal-state update. Three in-process attempts use exponential jitter. If DLQ publish or terminal update fails, the loop exits without committing so a restarted worker can retry; continuing and committing a later offset could otherwise skip the failed record. Docker Compose uses restart policies. Successful DLQ publication followed by terminal-update failure may duplicate the DLQ entry. Malformed messages go to a DLQ with SHA-256 and byte count rather than raw content. Broker access itself is not authenticated/encrypted in local Compose.

Practical limits: the dispatcher holds a DB transaction/lock during a bounded Kafka publish; pending-row scans can become a bottleneck and have no backpressure or retention policy. The OCR worker must be running even when its consumer is idle. `SKIP LOCKED` semantics were exercised with PostgreSQL in the native run, not under a multi-replica stress test. Reprocessing/versioned attempts and operator replay are not implemented; the unique `(analysis_id, topic)` key deliberately prevents an accidental second event for the same stage. No replica/failover or partition-rebalance certification is claimed.

The real local test stopped Kafka, accepted one upload, observed its unsent `certificate_uploaded` row in Postgres, restarted Kafka, and observed the analysis reach `completed`. It does not prove every failure window, worker crash, duplicate or multi-node scenario. Duplicate and callback/DLQ decisions also have isolated tests.

Worker events are validated against the stored owner, filename and content type. New outbox-backed analyses also require a matching committed stage event. Legacy analyses lacking an upload outbox use the bounded legacy-key path; null-owner records fail closed and require a recovery plan. Mismatched events are dead-lettered without marking the named analysis failed. This does not authenticate Kafka producers; broker ACLs, TLS and real multi-replica/failure tests remain necessary.
